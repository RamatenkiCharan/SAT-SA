PROJECT IDENTITY## 1.1 Project NameSAT-SAFull name:Supervisory Analytics Tool for SOC AssessmentSIH Problem Statement:26157Primary stakeholder:National Critical Information Infrastructure Protection Centre (NCIIPC)Primary assessed organizations:Critical Sector Entities (CSEs)Project category:Supervisory analytics and decision-supportDeployment target:NCIIPC-controlled local / offline / air-gapped environmentPrototype data strategy:Controlled synthetic datasets until authorized operational data is available.---# 2. ONE-SENTENCE PROJECT DEFINITIONSAT-SA analyzes submitted SOC operational evidence to identify potential execution gaps, negative-space conditions, contextual deviations, and review priorities so that human supervisors can focus their limited assessment effort where the evidence most strongly warrants attention.---# 3. CORE PROJECT IDENTITY## 3.1 Conceptual IdentityEvidence-to-Assurance## 3.2 Core Principle"Don't ask whether a SOC says it works.Analyze the evidence of how it actually operates."## 3.3 Core QuestionSAT-SA is fundamentally asking:&gt; Where does operational evidence warrant supervisory attention?It is NOT fundamentally asking:&gt; Is this SOC secure?It is NOT fundamentally asking:&gt; Can AI replace a security auditor?It is NOT fundamentally asking:&gt; Can we build another SOC dashboard?---# 4. PROBLEMNCIIPC supervisory assessments may involve manual review of SOC alert and case-management evidence.Important findings can exist inside operational records even when an organization appears healthy through:- policies- audits- self-assessments- management reports- KPI dashboards- compliance documentationAs the number of CSEs and the volume of operational records increase, exhaustive manual inspection becomes expensive and difficult to scale.SAT-SA therefore exists to reduce manual review effort while preserving evidence quality and human supervisory authority.---# 5. CORE INSIGHTThe project is based on a distinction between:DECLARATIVE CAPABILITY"What the organization says it does."andBEHAVIORAL / OPERATIONAL EVIDENCE"What the organization's operational records demonstrate."The system should therefore reason over evidence such as:- alerts- investigations- cases- escalations- actions- closures- recurrence- asset context- coverage- reporting periods- peer behaviorrather than relying primarily on self-reported maturity claims.---# 6. THE SAT-SA REASONING CHAINThe canonical reasoning chain is:EXPECTED&nbsp; &nbsp; ↓OBSERVED&nbsp; &nbsp; ↓GAP / ABSENCE&nbsp; &nbsp; ↓CONTEXT&nbsp; &nbsp; ↓EVIDENCE&nbsp; &nbsp; ↓UNCERTAINTY&nbsp; &nbsp; ↓SUPERVISORY PRIORITY&nbsp; &nbsp; ↓HUMAN REVIEWThe system must preserve this reasoning chain.A finding must never be reduced to:"AI says high risk."Instead, it should communicate:- what was observed- what was expected- what differs- what evidence supports the signal- what evidence contradicts it- what the data-quality limitations are- what contextual factors matter- how strongly the system recommends supervisory attention- which records the human should inspect---# 7. TWO CENTRAL ANALYTICAL CONCEPTS## 7.1 Execution GapAn execution gap exists when a documented or expected operational capability/process appears to exist, but operational evidence suggests weak, superficial, inconsistent, incomplete, or metric-driven execution.Examples:- unusually fast closure of severe events- expected escalation missing- repeated alerts without visible remediation- investigation evidence that appears insufficient- workflow shortcuts- KPI success inconsistent with deeper operational evidenceAn execution-gap signal is NOT automatically proof of wrongdoing or failure.It is a supervisory hypothesis supported by evidence.---## 7.2 Negative SpaceNegative space concerns evidence that should reasonably exist but is:- missing- unexpectedly sparse- inconsistent with the operating context- absent where source coverage appears adequateExamples:- critical assets with unexpectedly weak evidence coverage- expected alert categories absent despite adequate source coverage- missing investigation/escalation evidence for event classes where such evidence is normally expected- significant activity changes without adequate explanationNegative space is NOT equivalent to a missing database row.Negative-space logic must first ask:&gt; Is the source data itself sufficiently complete and representative?Only after data trust is established should operational absence be interpreted.Negative-space findings must be expressed as potential blind spots, not definitive failures.---# 8. WHAT SAT-SA ISSAT-SA IS:- a supervisory analytics layer- an evidence analysis system- a decision-support system- an operational evidence reconstruction system- a review-prioritization system- a human-in-the-loop assurance tool- a local/offline analytical platform- an evidence provenance platform---# 9. WHAT SAT-SA IS NOTSAT-SA IS NOT:- a SOC replacement- a SIEM replacement- a SOAR replacement- an EDR- a real-time attack detection platform- a national continuous-monitoring platform- a centralized telemetry collection system- a cloud SaaS platform- an externally hosted AI service- an autonomous cyber decision-maker- an auditor replacement- a generic maturity questionnaire- an "AI dashboard"- a chatbot disguised as an analytics engineThese boundaries are part of project identity, not optional implementation details.---# 10. PRIMARY VALUE PROPOSITIONThe primary value is:REDUCE MANUAL REVIEW EFFORTWHILEPRESERVING / CAPTURING A HIGH PROPORTION OF IMPORTANT CASESThe platform should help a supervisor move from:"Review everything."to:"Review these cases first, because the evidence suggests they are most worthy of attention."---# 11. PRIMARY SUCCESS METRICThe central measurable benefit is review efficiency.The key metric is:## Supervisory Review YieldConceptually:&gt; How much expert-important supervisory signal can be captured within a constrained review budget?Related evaluation metrics include:- precision- recall- F1- false-positive rate- top-K recall- ranking quality- review reduction- explanation coverage- reproducibilityIMPORTANT:Never invent performance numbers.Every reported number must come from an actual test run and must identify:- dataset- scenario composition- evaluation methodology- tuning/holdout separation- limitations---# 12. SYSTEM INPUTSBaseline structured inputs:- CSE information- reporting periods- asset inventory- alerts- investigations- cases- escalations- actions- closures- dispositions- coverage observations- contextual attributes used for peer groupingBaseline ingestion formats:- CSV- JSONOther interfaces may be added later only when they do not compromise the prototype's delivery priorities.---# 13. CANONICAL DATA MODELThe system should normalize source-specific structures into a canonical evidence model.Conceptually:CSE&nbsp;├── Asset&nbsp;│&nbsp; &nbsp; ├── criticality&nbsp;│&nbsp; &nbsp; ├── environment&nbsp;│&nbsp; &nbsp; └── expected monitoring context&nbsp;│&nbsp;├── Reporting Period&nbsp;│&nbsp;└── Alert&nbsp; &nbsp; &nbsp; ├── Investigation&nbsp; &nbsp; &nbsp; ├── Case&nbsp; &nbsp; &nbsp; │&nbsp; &nbsp; ├── Escalation&nbsp; &nbsp; &nbsp; │&nbsp; &nbsp; ├── Actions&nbsp; &nbsp; &nbsp; │&nbsp; &nbsp; └── Closure&nbsp; &nbsp; &nbsp; │&nbsp; &nbsp; &nbsp; └── recurrence / related alertsCore entities:- CSE- Asset- ReportingPeriod- Alert- Investigation- Case- Escalation- Action- Closure- CoverageObservation- PeerGroup- Finding- FindingEvidence- FindingSignal- ReviewDecision- Dataset- DatasetVersion- Ruleset- ModelVersion- AnalysisRun- Report- AuditEvent---# 14. SOURCE EVIDENCE PRINCIPLEOriginal source evidence must never be silently overwritten.Source evidence and derived analytical data must be logically separated.Every analysis must be traceable back to:- dataset version- source record- transformation/schema version- rule version- model version where applicable- analysis runA derived conclusion is not a substitute for source evidence.---# 15. DATA TRUST COMES BEFORE ANALYTICSData quality is a first-class analytical layer.Before trusting a finding, assess:- completeness- missingness- consistency- timestamp validity- identifier consistency- referential relationships- categorical validity- duplicate records- source coverage- asset coverage- alert-class coverage- investigation coverage- escalation coverage- representativenessData quality must influence confidence in findings.---# 16. CRITICAL NEGATIVE-SPACE RULENEVER do this:missing evidence&nbsp; &nbsp; =failureCorrect reasoning:missing evidence&nbsp; &nbsp; ↓check source/data trust&nbsp; &nbsp; ↓check expected evidence model&nbsp; &nbsp; ↓check coverage&nbsp; &nbsp; ↓check context&nbsp; &nbsp; ↓check peer behavior&nbsp; &nbsp; ↓check history&nbsp; &nbsp; ↓consider alternative explanations&nbsp; &nbsp; ↓generate potential blind-spot signal&nbsp; &nbsp; ↓human reviewPossible alternative explanations include:- source-system outage- schema mismatch- ingestion gap- reporting omission- retention issue- operational change- reclassification- incomplete asset inventory- incomplete telemetry- legitimate environmental difference---# 17. WORKFLOW RECONSTRUCTIONThe system should reconstruct operational sequences where relationships permit.Typical flow:ALERT&nbsp; ↓INVESTIGATION&nbsp; ↓CASE&nbsp; ↓ESCALATION&nbsp; ↓ACTION / RESPONSE&nbsp; ↓CLOSUREThe exact sequence may differ by available evidence.The platform must preserve missing-link uncertainty rather than inventing relationships.Workflow reconstruction should use:- identifiers- timestamps- foreign-key relationships- reporting periods- contextual relationships---# 18. EXPECTED-VS-OBSERVED REASONINGThe central analytical mechanism is:EXPECTED BEHAVIOR&nbsp; &nbsp; &nbsp; &nbsp; vsOBSERVED BEHAVIORExpected behavior may come from:- explicit supervisory criteria- configured domain rules- contextual expectations- historical baseline- peer baselineThe implementation must distinguish:- hard requirement- configured expectation- statistical baseline- inferred patternDo not silently treat all four as equivalent.---# 19. P0 CORE ANALYTICSThe P0 prototype must prioritize high-value, explainable analytical signals.Core P0 detectors include:### 19.1 Premature / Fast ClosureIdentify severe alerts/cases that close substantially faster than an appropriate baseline and lack supporting evidence.### 19.2 Escalation GapIdentify high-severity events for which expected escalation evidence is absent.### 19.3 Repeated Unresolved AlertsIdentify recurring alerts associated with the same asset or context where visible remediation evidence is insufficient.### 19.4 Negative-Space / Coverage GapIdentify expected-but-missing or unexpectedly sparse evidence while accounting for data trust and contextual uncertainty.### 19.5 Peer GroupingGroup comparable CSEs using contextual attributes.P0 peer-context features may include:- sector- scale- asset count- alert volume- relevant operating characteristicsDo not compare materially different CSEs using naive universal thresholds.---# 20. P1 / P2 ANALYTICSPotential deeper analytical capabilities include:- investigation sufficiency- repetitive/template-like investigations- workflow shortcut detection- metric-quality analysis- persistence analysis- broader temporal analytics- change-point detection- sequence analytics- advanced outlier analysis- ML anomaly detection- more advanced supervised ranking- deeper governance and audit capabilitiesThese are not allowed to displace unfinished P0 work.---# 21. PEER BENCHMARKING PRINCIPLEUniversal thresholds are unsafe because CSEs differ in:- scale- sector- asset population- alert volume- SOC operating model- environmental complexityTherefore:compare against appropriate peersrather thancompare against one universal numberPrefer:- normalized measures- peer distributions- robust statistics- minimum sample sizes- percentiles- deviations from peer behaviorThe system should explain:- who the peers are- why those peers were selected- how the entity differs- how strong the comparison is- what uncertainty exists---# 22. EVIDENCE FUSIONSAT-SA must NOT create an opaque single "AI risk score."The intended concept is a transparent supervisory-priority mechanism.Conceptually:Priority=weighted evidence signals+ persistence+ peer deviation+ impact/criticality+ workflow severity- data uncertainty- contradicting evidenceWeights and thresholds must be:- explicit- versioned- reviewable- reproducibleThe UI should expose major contributing signals.---# 23. THREE DIFFERENT CONFIDENCESNever confuse:## Source Data Quality"How trustworthy / complete is the underlying data?"## Finding / Evidentiary Confidence"How strongly does the available evidence support this supervisory signal?"## Model Confidence"How confident is a machine-learning model in its own prediction?"These are different concepts.Model confidence must never automatically become evidentiary confidence.---# 24. CONTRADICTING EVIDENCEThe analytical system must represent evidence that weakens a finding.Examples:- known data outage- incomplete asset inventory- small sample size- unusual but explained operational change- missing source system- peer comparison instability- conflicting operational evidenceA good finding contains both:SUPPORTING SIGNALSandCONTRADICTING / LIMITING SIGNALS---# 25. HUMAN-IN-THE-LOOP PRINCIPLEHuman supervisory judgement remains authoritative.SAT-SA:DISCOVERS→EXPLAINS→PRIORITIZES→SUPPORTS REVIEWSAT-SA does not:DECLARE GUILTorDECLARE SECURITY FAILUREorREPLACE THE SUPERVISORPreferred wording:- "potential execution gap"- "potential blind spot"- "supervisory attention recommended"- "evidence warrants manual review"- "signal weakened by data-quality limitation"Avoid unsupported language such as:- "CSE is insecure"- "CSE is negligent"- "fraud confirmed"- "AI proved failure"---# 26.
